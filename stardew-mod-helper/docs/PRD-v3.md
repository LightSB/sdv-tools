## 2. Tab 组织建议（本次关键决策）

**推荐：底部由 2 个 Tab 扩为 3 个——「下载」/「工作区」/「历史」**，本次全部新能力都收进「工作区」一个 Tab，内部用顶部分段控件（Segmented）分三块：

| 分段 | 承载内容 | 对应需求 |
| --- | --- | --- |
| ① 本地模组库 | 上传入口（方式 A/B）＋ 模组清单卡片 ＋ 更新状态 ＋ 勾选打包入口 | R33–R39、R43、R45 |
| ② N 网搜索 | 搜索框 ＋ 结果卡片 ＋「下载 / 加入清单」 | R40–R42 |
| ③ 待下载 & 打包 | 来自搜索的待下载清单 ＋「打包所选」操作与进度 | R42、R43、R44 |

**为什么这样组织**：

- iOS 底部导航 3 个已是舒适上限，再加会拥挤且触控区变小；工作区内部用分段比加 Tab 更聚焦。
- 打包是"模组库的自然延伸"（先有本地模组才能打包），与模组库同处一个 Tab，减少跨 Tab 心智负担。
- 搜索与打包刻意分开：搜索结果**没有本地文件树，不能直接打包**（见 R42 边界说明），避免用户误解。

**跨 Tab 协作约定**：

- 搜索结果点「下载」→ 切回「下载」Tab，用该 `modId` 走 v1 的 `resolveMods` 流程（Premium 直下 / 非 Premium 降级不变）。
- 搜索结果点「加入清单」→ 留在工作区「待下载 & 打包」，仅作为待办记录。

**备选（不推荐）**：拆成 4 Tab（下载 / 模组库 / 搜索 / 历史），导航更拥挤，且搜索与打包割裂。

## 4. 各变更详细说明与交互预期

### 4.1 R32【修改】「工作区」Tab 与状态骨架

- **Tab 结构**：`TabKey` 由 `'download' | 'history'` 扩为 `'download' | 'workspace' | 'history'`；`TabBar` 顺序为 下载 → 工作区 → 历史，图标沿用田园线性风格。
- **渲染**：`App.tsx` 主区在 `download` 与历史之外新增 `workspace` 分支，渲染「工作区」面板；`StatusBar` 与 API Key 状态徽标保持全局可见（更新检测 / 搜索都依赖已校验的 Key）。
- **状态扩展**：`AppState` 新增 `localMods`、`selectedPackIds`、`searchState`、`uploadProgress`、`packProgress` 等字段（详见第 5 节），初始值均为空 / idle。
- **持久化约定**：API Key / 主题 / 历史沿用现有 `useLocalStorage`；**模组文件树与 Blob 不进 localStorage**（体积原因），见第 6 节与待确认 Q1。
- **回归底线**：`download` / `history` 两分支代码与行为不改动。

### 4.2 R33 / R34【新增】两种上传方式

**入口**：工作区「本地模组库」分段顶部并列两个按钮——「上传整个 Mods 文件夹（zip）」与「上传单个模组 zip」，下方说明 iOS 操作提示："在「文件」App 中长按 Mods 文件夹 → 压缩为 zip 后上传"。

- **方式 A（R33）**：
  1. 用户选择单个 zip；前端读为 `ArrayBuffer`，用 JSZip 加载并解压（需新增 `jszip` 依赖）。
  2. 遍历 zip 顶层：每个**顶层子文件夹**视为一个模组（忽略 `__MACOSX`、`.DS_Store` 等系统项）；若顶层直接是文件而非文件夹，则整体视为一个"无文件夹"模组并提示。
  3. 每个模组读取其根下 `manifest.json`（见 R35），构建 `LocalMod` 的文件树。
- **方式 B（R34）**：
  1. 用户可多选 zip；每个 zip 视为一个模组。
  2. 兼容常见结构：zip 内若只有一层同名文件夹则剥离该层作为模组根；否则以 zip 名为模组名兜底。
  3. 与方式 A 的结果合并进同一 `localMods`；若 `UniqueID` 或名称重复，提示"检测到 N 个可能重复的模组"，由用户决定是否保留。
- **共同约束**：解压全程在内存完成；损坏 / 加密 zip 捕获异常并 Toast 友好提示，不影响已成功上传的其他文件；上传按钮在解压期间禁用防重复提交。

### 4.3 R35【新增】`manifest.json` 解析

- **来源**：SMAPI 标准 `manifest.json`，位于每个模组文件夹根。
- **提取字段**：`Name`（模组名）、`Author`（作者）、`Version`（版本）、`Description`（摘要）、`UpdateKeys`（更新键数组）、`UniqueID`（去重辅助，可选）。
- **解析容错**：
  - 文件缺失 / JSON 解析失败 → 该模组标记 `manifest: null`，名称用文件夹名兜底，更新状态 `unknown`，原因="未找到有效的 manifest.json"（R39）。
  - `UpdateKeys` 可能是字符串或数组；数组元素形如 `Nexus:1915`、`Nexus:2400@GeodeCrusher`，提取时**去掉 `@` 及其后子键**，只保留数字 modId 并去重。
  - 非 `Nexus:` 前缀的键（如 `GitHub:`、`ModDB:`）本次不处理，仅保留原始值展示，更新检测时忽略（列为待确认 Q3）。
- **副作用**：不写回、不修改用户上传的任何文件内容。

### 4.4 R36【新增】本地模组库清单卡片

**一张卡片长这样**（自上而下）：

| 区域 | 内容 |
| --- | --- |
| 顶部左 | 左上角勾选框（打包用）；模组名（大字号，粗体）；来源徽标「文件夹上传 / 单包上传」 |
| 顶部右 | 更新状态徽标（见 4.5） |
| 信息行 | 作者 · 版本 v{Version} · 文件数 / 总大小 |
| UpdateKeys 行 | 彩色小标签展示原始 UpdateKeys（如 `Nexus:2400`、`Nexus:1915`）；点击可跳对应 N 网页 |
| 文件树摘要 | "包含 N 个文件" 可展开查看路径与大小（默认收起，避免长列表） |
| 操作行 | 「更新检测」「打开 N 网」（有 modId 时）「移除」；outdated 时「打开 N 网」高亮为「查看新版本」 |
| 说明区 | unknown 时显示灰底原因条（R39） |

- **列表能力**：顶部搜索框（按名称 / 作者 / UpdateKeys 过滤）；排序切换（名称 A–Z、更新状态：outdated 优先）；显示"共 N 个模组，已勾选 M 个"。
- **勾选语义**：勾选仅用于打包 R43，不影响更新检测；勾选状态存 `selectedPackIds`。

### 4.5 R37 / R38 / R39【新增】更新检测与状态标记

**检测流程（每个模组）**：

1. 取 `LocalMod.updateKeys`，提取所有 `Nexus:<modId>`（去 `@子键`）→ `nexusModIds`。
2. 对每个 modId 调现有 `fetchFiles(modId, apiKey)`；在返回列表中选 `is_primary = true` 的文件（多个则取 `uploaded_at` 最新者）；若无主文件则取 `uploaded_at` 最新者作为候选。
3. 得到 `latest = { modId, version, uploadedAt, fileId }`。
4. **比对判定**（优先级从高到低）：
   - 本地 `Version` 与 `latest.version` 均可解析为数字版本号 → 逐段比较：相等 `latest`，本地低 `outdated`，本地高 `latest`（标记"本地更新"可不提示）。
   - 版本号不可解析 → 退回时间比较：以该模组的 `lastCheckedAt`（首次则以 `addedAt` 上传时刻）为基准，`latest.uploadedAt` 晚于基准 → `outdated`，否则 `latest`。
   - 多个 modId：任一 `outdated` 则整体 `outdated`（取最新版本最高者展示）；全部一致 → `latest`；全部请求失败 → `unknown`。
5. 结果写入 `updateInfo` 与 `lastCheckedAt`；**不调用 `download_link.json`，不下载任何文件**。

**状态标记（徽标规范）**：

| 状态 | 徽标 | 交互 |
| --- | --- | --- |
| `latest` | 绿色 chip「已是最新」 | 静态；附最近检测时间 |
| `outdated` | 橙色 chip「有新版本 v{latest.version}」 | 高亮按钮「查看新版本 / 打开 N 网页面」，跳转 `mods/{modId}` 页；不自动下载 |
| `unknown` | 灰色 chip「无法检测」 | 展开/悬停显示原因：无 manifest / 无 UpdateKeys / 无 N 网条目 / 401 / 429 / 网络错误 |
| 检测中 | 旋转图标 +「检测中」 | 按钮禁用，逐条更新状态 |

**R39 特殊说明**：`manifest: null` 或无 `Nexus:` UpdateKeys 的老式模组，检测时直接置 `unknown` 并显示固定文案："此模组缺少 manifest.json 或 UpdateKeys，无法自动检测更新，请到 N 网手动查看。"该模组不发起任何请求，也不拖累批量检测。

### 4.6 R40 / R41 / R42【新增】N 网搜索、展示与加入清单

**端点接入（R40）**：

- 路径生成：`apiPath.search(query)` → `/games/stardewvalley/mods/search.json?game_id=1303&searchQuery=<encodeURIComponent(query)>`。
- 建议在 `config/index.ts` 增加 `gameId: 1303`，路径中 `game_id` 引用该常量（与现有 `gameDomain` 并列），避免硬编码。
- 经现有 `request<T>` 调用，自动注入 `apikey` / `Application-*` 头与错误归一化；`SearchResponse` DTO 放入 `types/nexus.ts`（字段含 `mods`、`pagination`）。
- 前置校验：搜索前要求 API Key 已校验（复用 `keyStatus === 'valid'` 守卫），未校验则引导配置，不发起无效请求。

**结果展示与限频（R41）**：

- 搜索框：输入防抖 ≥ 500ms，或提供「搜索」按钮手动触发（二选一，推荐防抖 + 回车触发）；空关键词不请求。
- 结果卡片：缩略图（`onError` 走田园占位）、名称、作者、摘要（2 行截断）、下载量、endorsements、分类。
- 分页：每页 ≤ 20 条；底部「加载更多」手动翻页（`page` 递增），**不做无限滚动自动预加载**；累计上限（建议 100 条）到达后提示"结果较多，请细化关键词"。
- 限频处理：HTTP 429 → `searchState.rateLimited = true`，显示"请求过于频繁，请稍后再试"并临时禁用搜索按钮（建议冷却 10–30s）；网络错误可重试。

**加入清单与下载复用（R42）**：

- 每张结果卡两个主操作：
  - **「下载」**：切到「下载」Tab，把 `modId` 交给 `resolveMods`（把该 ID 设为 `idsInput` 并解析），后续沿用 v1 文件选择 / 汉化 / 前置 / Premium 降级全流程；成功后照常写历史。
  - **「加入清单」**：向工作区「待下载 & 打包」追加一条 `PendingDownload`（来源=search、`inList=true`）；已加入的显示「已在清单」并禁用重复加入。
- **清单能力**：展示已加入项（名称 / modId / 缩略图）、逐条移除、「全部下载」批量触发（逐条走 v1 `buildDownloadPlan`，遵循 Premium/降级策略与 Key 守卫）。
- **边界（必须让用户看懂）**：清单项来自 N 网、**没有本地文件树，因此不参与打包**；卡片上用浅色说明条写明"下载并在「文件」App 解压、通过上方上传后，才可作为本地模组打包"。

### 4.7 R43【新增】整合打包

**操作流程**：

1. 在「本地模组库」勾选若干模组（仅 `fileTree` 非空者可选；搜索待下载项不可选，见 R42 边界）。
2. 点击「打包所选」→ 弹二次确认层：列出模组名、数量、文件总数、预估总大小。
3. 前端用 JSZip 新建 zip：**以每个模组名为顶层文件夹名**（做文件名安全化：去除 `/ \ : * ? " < > |` 等非法字符、去首尾空格、空名用 `mod-{id}` 兜底），把该模组解压后的文件树**原样放入**该文件夹下（保持相对路径与层级）。
4. 显示进度（已处理文件数 / 总文件数）；完成后生成 Blob 并触发 `a.download`，文件名形如 `stardew-mods-pack-2026-xx-xx.zip`。
5. 完成 Toast：**"已打包：解压后把文件夹放进游戏的 Mods 目录即可使用"**。
6. 空勾选时按钮禁用并提示"请先勾选要打包的模组"。

**关键约束**：打包只重组**用户本地上传并解压出的文件夹**，不联网、不重新下载；若两个模组同名，自动加后缀 `-2` 并提示，避免 zip 内覆盖。

### 4.8 R44【新增】iOS 体验与进度反馈

- **阶段反馈**：上传读取、解压、`manifest` 解析、更新检测、打包各阶段用进度条 / 骨架屏 / 旋转图标；长操作期间按钮禁用防重复提交。
- **大小提示**：单个 zip 建议阈值 **100MB**（可配置），超过时显示"文件较大，处理可能需要一点时间，请保持页面在前台"；检测到明显超大（建议 300MB）时二次确认。
- **空状态**：无模组时田园风空状态（叶片/幼苗 SVG + "上传 Mods 文件夹或单个模组 zip 开始管理"）；无搜索结果时"换个关键词试试"。
- **错误降级**：损坏 zip / 解密失败 / 429 / 网络错误均有具体文案与「重试」入口；不出现白屏或静默失败。
- **触控与适配**：所有按钮触控区 ≥ 44px；底部 Tab 保留 `env(safe-area-inset-bottom)`；沿用 v2 浅色田园配色与 chip 规范。

### 4.9 R45【新增】更新结果缓存与批量检测节流

- **缓存**：每个 `LocalMod` 存 `lastCheckedAt` 与 `updateInfo`；进入工作区**不自动重检**，直接展示缓存结果；仅点「更新检测」/「重新检测」或顶部「检测全部」时刷新。
- **批量节流**：「检测全部」按并发上限（建议 ≤ 3）逐条执行；每条独立更新状态与错误，单条失败可重试，不整体回滚。
- **防抖/去重**：同一 modId 在缓存有效期内（建议 10 分钟）不重复请求；手动「重新检测」才强制刷新。

## 5. 数据结构预期（字段建议，非 TS 代码）

> 以下为架构师实现时的字段契约建议；命名可在落地时按项目风格微调，但语义与状态机需保持一致。

### 5.1 `LocalMod`（本地模组，R33–R39 / R43）

| 字段 | 说明 |
| --- | --- |
| `id` | 本地唯一标识（上传时生成的 UUID），用于勾选与定位 |
| `name` | 模组名：优先 `manifest.Name`，无则用文件夹名 / zip 名兜底 |
| `author` | 作者：`manifest.Author`，缺省为空串 |
| `version` | 本地版本：`manifest.Version`，缺省为空串 |
| `description` | 摘要：`manifest.Description`，缺省为空串 |
| `manifest` | 原始解析对象或 `null`（无 / 解析失败时为 `null`，用于 R39 判定） |
| `updateKeys` | 原始 UpdateKeys 数组（保留 `Nexus:2400@X` 原样，供展示） |
| `nexusModIds` | 提取出去重后的数字 modId 数组（去 `@子键`、仅 `Nexus:` 前缀），供检测与跳转 |
| `fileTree` | 文件树节点数组：每个节点含 `path`（相对路径）、`size`（字节）、`kind`（file / dir）；打包时按此还原结构 |
| `fileCount` / `totalSize` | 汇总：文件数、总字节数（卡片展示与大小提示） |
| `rootFolder` | zip 内顶层文件夹名方式 A 下的模组根名（用于去重与展示） |
| `source` | 来源枚举：`folder-zip` / `single-zip` |
| `uniqueId` | `manifest.UniqueID`，用于重复检测，可空 |
| `updateStatus` | 更新状态：见 5.2 |
| `updateInfo` | 最新结果：`{ modId, version, uploadedAt, fileId }` 或 `null` |
| `checkError` | 检测失败 / 无法检测原因文案；`unknown` 时必填 |
| `lastCheckedAt` | 最近检测时间（ISO 字符串），`null` 表示未检测 |
| `addedAt` | 加入本地库时间（ISO 字符串），首次检测的时间基准 |
| `selected` | 是否勾选打包（亦可只存于 `selectedPackIds`，二选一） |

### 5.2 `UpdateStatus`（更新状态，R37–R39）

| 取值 | 含义 | 备注 |
| --- | --- | --- |
| `latest` | 已是最新 | 缓存有效期内不重检 |
| `outdated` | 有更新 | 附 `updateInfo`，提供打开 N 网 |
| `unknown` | 无法检测 | 附 `checkError` 说明原因（无 manifest / 无 UpdateKeys / 无条目 / 401 / 429 / 网络错误） |

> 检测中的 UI 态建议用独立的 `checkingIds` 集合或局部 `isChecking` 标志，不占 `UpdateStatus` 三值，避免污染持久化数据。

### 5.3 `SearchState`（搜索状态，R40–R42）

| 字段 | 说明 |
| --- | --- |
| `query` | 输入框当前关键词 |
| `activeQuery` | 防抖后实际请求的关键词（空则不请求） |
| `results` | 结果数组，元素见 5.4 `SearchResult` |
| `page` | 当前页码，从 1 开始 |
| `hasMore` | 是否还有下一页（据 `pagination` 判定） |
| `total` | 结果总数，用于上限提示 |
| `loading` / `error` | 加载中标志 / 错误文案 |
| `rateLimited` | 是否触发 429，触发时禁用搜索并进入冷却 |
| `lastSearchAt` | 上次请求时间，用于频率控制 |

### 5.4 `SearchResult`（搜索结果项，R41 / R42）

| 字段 | 说明 |
| --- | --- |
| `modId` | N 网模组 ID（用于下载与跳转） |
| `name` / `author` | 名称 / 作者名（作者来自 `authors` 数组，复用 `formatAuthors` 风格） |
| `summary` | 摘要，UI 2 行截断 |
| `thumbnailUrl` | 缩略图 `picture_url`，失败走田园占位 |
| `downloads` / `endorsements` | 下载量 /  endorsed 数，格式化展示 |
| `categoryName` | 分类，可空 |
| `inList` | 是否已加入待下载清单（防止重复加入） |

### 5.5 `PendingDownload`（待下载清单项，R42）

| 字段 | 说明 |
| --- | --- |
| `modId` | N 网模组 ID |
| `name` / `thumbnailUrl` | 展示用名称与缩略图 |
| `source` | 固定为 `search` |
| `addedAt` | 加入时间 |

## 6. 隐私与性能说明

### 6.1 隐私（强约束）

- **模组文件绝不上传服务器**：解压、`manifest` 解析、文件树维护、更新比对、打包全部在浏览器本地内存完成；不存在任何把模组 Blob 发往远端的路径。
- **API Key 仅本地**：沿用现有 `request` 注入请求头的方式，Key 只存设备 `localStorage`、只随必要的 Nexus 请求发往 Nexus 官方 API；**不进日志、不进 Toast 详情、不写入任何模组元数据或埋点**。
- **网络请求边界**：本次新增的对外请求仅两类——`search.json`（用户主动搜索）与 `files.json`（更新检测，仅传 modId）。二者都只发标识符 / 关键词，不发文件内容。
- **不引入第三方埋点 / 分析 SDK**；新增依赖仅 `jszip` 等纯前端库。

### 6.2 性能与限制建议

- **zip 大小**：建议单包软阈值 100MB（提示）、硬提示 300MB（二次确认）；JSZip 解压在内存进行，超大包可能导致 iOS Safari 内存压力，需在 UI 明确提示。
- **文件树持久化**：`localStorage` 只存 Key / 历史 / 主题 / 上次 ID；模组文件树与 Blob **不写 localStorage**。会话内维护在内存；是否用 IndexedDB 持久化完整文件树 / Blob 以支持跨会话打包见待确认 Q1。
- **速率限制**：搜索有速率限制——输入防抖 ≥ 500ms、手动「加载更多」、结果上限、429 冷却；更新检测对同一 modId 设缓存有效期（建议 10 分钟）与并发上限（建议 ≤ 3），避免批量触发限流。
- **大列表渲染**：模组库与结果列表在数量大时采用限制展示 / 分页 / 虚拟列表（P1，视规模决定），避免一次性渲染过多卡片。
- **失败隔离**：单个模组解析或检测失败不影响其余模组，沿用 v1 `Promise.allSettled` 风格的错误隔离思路。

## 8. 待确认问题（含推荐）

| # | 问题 | 推荐 |
| --- | --- | --- |
| **Q1** | 解压后的文件树 / Blob 是否跨会话持久化（IndexedDB）？ | 推荐 **v3 先只在内存维护、不持久化完整 Blob**，刷新后需重新上传；模组清单元数据（不含文件）可存 IndexedDB 以便展示。理由：规避 iOS 存储配额与实现复杂度。若用户强烈需要"关掉再开还能打包"，再单独排期做 IndexedDB 持久化。 |
| **Q2** | 更新检测的版本比对以版本号还是时间为准？ | 推荐 **版本号优先、时间兜底**（见 4.5），兼顾准确与兼容；本地版本高于线上时不提示"有更新"。 |
| **Q3** | 非 `Nexus:` 的 UpdateKeys（GitHub / ModDB 等）如何处理？ | 推荐 **v3 仅展示原始值、不检测、不计入 unknown 的错误原因**；有 `Nexus:` 键时按 Nexus 检测，完全没有时按 R39 说明。后续版本再扩展来源。 |
| **Q4** | 搜索结果「加入清单」是否需要持久化？ | 推荐 **会话内内存维护即可**，不做 localStorage 持久化；与待下载语义一致，降低复杂度。 |
| **Q5** | 「全部下载」批量触发在 iOS Safari 可能被拦截多次下载。 | 推荐 沿用 v1 策略——逐个触发并提示"允许多个下载"；非 Premium 逐条降级为打开 N 网 / 复制链接，不假装直下。 |
| **Q6** | 打开 N 网页面跳模组主页还是文件页？ | 推荐 **跳模组主页 `mods/{modId}`**（更新检测只需让用户自行查看/下载最新版本，无需锁定 fileId）；若后续要精确跳文件页可再加。 |
| **Q7** | 打包 zip 的顶层文件夹用 `manifest.Name` 还是原文件夹名？ | 推荐 **优先原文件夹名**（即用户游戏中的实际目录名），无文件夹名时用 `Name` 兜底；这样打包回去不会改变游戏内目录结构，减少出错。 |
| **Q8** | 搜索限频冷却时长与结果上限的具体数值？ | 推荐 冷却 **10–30 秒**、单轮结果上限 **100 条**、每页 **20 条**、防抖 **500ms**；数值集中到 `config` 便于调整。 |
